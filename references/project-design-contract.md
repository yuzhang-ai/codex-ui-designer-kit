# 项目设计契约：从规范到实现

新建或整体改造在写页面前读取本页；局部任务只检查受影响的角色，沿用项目事实。不要求用户提供设计术语，也不要求为了填表扩大产品范围。

## 1. 先确定本项目的系统

视觉方向按 [设计推导](visual-design-derivation.md)形成；下表承接为工程约定，不替代定位和风格判断。

在 DESIGN 中写一份短契约，使用实际值和代码位置，不只写“简洁、统一、高级”。已有系统先引用并补缺口。至少覆盖本次范围需要的内容：

| 契约 | 必须落定 | 如何核验 |
|---|---|---|
| 注意力 | 每页主任务、第一视觉重点、主操作；常驻/按需/删除的信息 | 同一真实内容截图中，强调元素是否都服务当前任务 |
| 排版与布局 | 标题/正文/元信息的字族/回退、字重、字号、行高、字距；列宽、间距角色与断点变化 | 实际字体、长标题、窄屏，不以品牌截图猜像素 |
| 色彩与表面 | 文字/背景/强调/错误的token；边框、阴影分别用于什么关系 | 对比检查；解释哪些对象需要容器、哪些无需容器 |
| 图标语言 | 对象/动作/状态的图标映射；家族、笔画/填充、光学大小、标签、点击区域 | 真实尺寸与中英文字基线；同义同图、选中与完成可区分 |
| 操作组件 | 主/次/低频/危险操作的角色与组件variant；大小、焦点、禁用、选中 | 同角色跨页一致，状态可区分，键盘可达 |
| 内容与状态 | 标签、常驻提示、按需帮助、错误和成功反馈的出现条件 | 触发真实事件，检查下一步、输入保留与反馈时机 |

项目选定值是该项目默认值，不是所有产品的通用配方。阅读页可以正文为第一重点而没有强色主按钮；营销页可以以叙事为重点。线框、实底、阴影或衬线字体都不是禁项，选择须说明角色与场景。

## 2. 用代码兑现，避免每页重想一遍

将契约映射到项目现有tokens、样式角色和共享组件。没有现成系统时建立最小可复用实现：例如 Button 的 primary/secondary/quiet/danger 角色、Field 的标签/帮助/错误位置、页面标题和内容容器。静态HTML可用共享CSS类，不强制组件框架或创建无用组件库。

DESIGN记录“角色 → token/组件 → 代码位置 → 适用页面”。相同角色不按页随意添加字号、圆角、边框和反馈方式；确有不同任务时记录例外原因。先让代表页的默认态和关键非成功态通过，再扩展其他页。局部修改只检查受影响的共享角色及其使用处。

交互沿用 interaction-contracts.md；为实际动作填写触发、反馈、数据、恢复、焦点去向和验证证据。不把有按钮、静态状态图或成功toast当作交互完成。

## 3. 交付前主动做注意力审查

看实际页面，而不是只读实现说明。按以下问题做一次有记录的取舍，不机械追求删除数量：

- 常驻文字：它帮助当前决策、输入或恢复吗？同一信息是否已在标题、导航或状态中出现？重复解释合并；低频帮助按需出现。保留必要标签、错误、权限后果和能力边界，不能把必要信息藏成仅悬停可见。
- 强调元素：主色、实底、边框、阴影、编号、图标和动效分别把注意力引向哪里？弱化与主任务竞争的次要操作；保留可发现性和焦点。
- 容器与分组：卡片/线条是否表示真实对象或层级？仅靠间距已能清楚分组时，避免叠加没有额外职责的装饰；不能用一律去边框破坏表单可辨识性。
- 默认与异常：默认页避免堆满教学；需要时再显示操作反馈，错误仍具体可恢复。检查精修是否只覆盖成功态。

记录最影响任务的具体观察、采用/不采用的修改及代码或截图证据。没有发现问题也说明检查的页面/状态，不编造修复。不要把基础问题留给用户以“审美验收”名义逐项发现。

例如：笔记阅读页同时出现英文眉题、中文标题、同义面包屑、标语与章节编号时，先保留定位和阅读需要的部分，再判断其他元素的作用；商品购买页的配送说明或错误提示不能因为“字多”照此删除。

## 4. 可交付判断

功能、系统一致性和注意力审查分开。发现任务被辅助内容压住、同角色跨页漂移、状态误导等可明确解释的缺陷，先修再复核。修复次数沿用Skill上限；仍有缺口可以交付Candidate，但不得标记“视觉通过”。

机器检查适合token使用、可运行性、几何和状态；Agent看截图判断层级与取舍；用户判断品牌偏好和产品方向。独立评审在工具可用且获授权时使用，否则自审并标注。任何评审都不能保证审美一次命中。
